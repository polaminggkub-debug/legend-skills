Reference 02

เช็กลิสต์จาก brief ถึง post-merge

ใช้เป็นแผ่นตรวจรับงานหนึ่งชิ้น เขียนหลักฐานหรือช่องว่างลงไป อย่าใช้เครื่องหมายถูกแทนผลรันจริง

ช่วงต้องตอบหลักฐานที่ควรเก็บสถานะ/ช่องว่าง
1. Provenance
บท 1		ใคร/ระบบใดสร้างหรือรีวิว contribution?PR actor, opening comment, commit trailer, session URLเขียน fact และข้อจำกัด
2. Goal & scope
บท 2		ผู้ใช้เห็นผลอะไร? ใครอยู่นอกขอบเขต?reproduction, target, non-target, deferred workมีจุดหยุดถามหรือไม่?
3. Decomposition
บท 3		งานย่อยส่งต่อกันอย่างไร? contract ใครเป็นเจ้าของ?owner, output, dependency, completion criterionชนกันตรง interface หรือไม่?
4. AC
บท 4		พฤติกรรมผ่าน/ไม่ผ่านสังเกตอย่างไร?Given/When/Then, boundary, failure, negative caseสร้าง implementation ผิดที่ยังผ่านได้ไหม?
5. Evidence
บท 5		ตรวจด้วยอะไร ที่ revision ไหน ผลเป็นอย่างไร?AC → assertion → command → SHA/time → result → limitationแยก claim จาก run จริง
6. Review
บท 6		finding แต่ละข้อ valid, invalid หรือ deferred?trigger, decision, patch commit, rerun result, follow-upfinal head ยังมี finding เก่าหรือไม่?
7. Merge
บท 7		อะไรผ่านจริงบน revision ที่จะรับ?check status, skipped/failure, approval, final diff, merge eventstale SHA หรือ missing log?
8. Post-merge
บท 8		artifact ที่ผู้ใช้ได้รับทำงานกับ consumer จริงหรือไม่?packaged install, migration from old state, probe, hardware/user reportแยก observation จาก causal claim
คำตัดสินรับงาน

พร้อมรับเมื่อ AC ที่จำเป็นผ่านด้วย evidence ที่ผูกกับ final revision ส่วนข้อยกเว้นต้องมีคำตัดสินจากผู้รับผิดชอบพร้อมเหตุผลและผลกระทบ การเขียนช่องว่างไว้เฉย ๆ ยังไม่ทำให้พร้อมรับ

สัญญาณให้ส่งกลับ

PR body บอกว่าผ่านแต่ไม่มี run, review ผูกกับ head เก่า, test mirror implementation, หรือ manual workaround แทน artifact ที่จะ merge
