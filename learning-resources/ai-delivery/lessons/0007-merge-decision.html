ทักษะที่ใช้กับงานจริง

ตัดสินใจ merge จาก revision ที่จะรับจริง

approved, checks และ merged เป็นคนละชั้นของหลักฐาน

ผลที่ฝึกได้ในบทนี้ คุณจะอ่าน head SHA, check status, approval และ merge event แยกกัน

ก่อน merge ให้ตรวจห้าชั้น: requirement ครบหรือมีข้อยกเว้น, finding สำคัญปิดหรือมีเหตุผล, tests มีผลจริง, ผลผูกกับ revision ที่จะรับ, และ final diff ถูกอ่านแล้ว

อย่าใช้คำว่า “CI ผ่าน” แบบไร้เวลาและ SHA check ที่เก่าอาจกลายเป็น stale หลัง push; check ที่ skipped หรือ neutral อาจผ่านกติกา required status แต่ไม่ได้รัน assertion ที่คุณต้องการ ส่วน merged_at และ merge commit เป็นหลักฐานว่าอะไรถูกนำเข้าไปจริง

ประโยคตัดสินใจที่ดี
“รับที่ head SHA X เพราะ AC1/AC2 มี evidence; check Y skipped จึงไม่ใช้เป็น proof; manual path Z ยังไม่มีหลักฐาน จึงส่งกลับไปตรวจหากเป็น AC ที่ต้องผ่านก่อนรับงาน”

เคส Omarchy #6093 เตือนว่า PR ที่ปิดโดยไม่ merge ไม่ควรเล่าเป็นงานที่ถูกรับ แม้มี diff และคำอธิบายละเอียด

แหล่งต้นทางหลัก

GitHub: Troubleshooting required status checks

อ่านเพื่อดู: เข้าใจความต่างของ head checks, skipped/neutral และเงื่อนไข merge

จำไว้

human approval ไม่ได้ลบข้อจำกัดของ evidence; เขียนสิ่งที่ผู้อนุมัติยังไม่ได้ตรวจด้วย

ลองตอบก่อนดูเฉลย

ข้อใดควรเป็นหลักฐานสุดท้ายของสิ่งที่ repository รับเข้าไปจริง

เลือกคำตอบหนึ่งข้อ

ลงมือกับงานของคุณ

เขียน merge decision สั้น ๆ จากสถานการณ์สมมติที่มีหนึ่ง check ผ่าน, หนึ่ง check skipped และหนึ่ง AC ยังไม่มีหลักฐาน

เกณฑ์ตรวจตนเอง
  • ระบุ revision ที่ตรวจ
  • แยก passed, skipped และ missing evidence
  • บอกว่าจะ merge, ส่งกลับ หรือเลื่อนอะไร
  • ไม่ใช้ approval เป็นคำตอบแทน business proof

ถามครูได้เสมอ: ถ้าคำศัพท์หรือหลักฐานชิ้นไหนยังไม่ชัด ให้ถามต่อพร้อมคัดลอกประโยคหรือ link ที่ติดขัด ครูจะช่วยแยกข้อเท็จจริงจากข้อสังเคราะห์ให้
