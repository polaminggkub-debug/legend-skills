ทักษะที่ใช้กับงานจริง

เขียน acceptance criteria ให้จับความผิดได้

AC เป็น requirement; test เป็นเพียงวิธีหนึ่งในการหาหลักฐาน

ผลที่ฝึกได้ในบทนี้ คุณจะเขียน AC แบบ Given/When/Then พร้อม boundary และ negative case

AC ที่ดีบอก behavior ที่รับได้ก่อนเห็น patch ใช้รูปแบบ Given → When → Then และเลือก observable ที่แยก “ถูก” กับ “ยังผิด” ได้ เช่นไม่ใช่ “reset สำเร็จ” แต่เป็น “ระหว่างงานกำลังคลายตัว DB ยังเปิด และเมื่อถึง bound จึงปิด”

ใส่กรณีปกติ, boundary, failure และ non-target อย่างน้อยหนึ่งแบบ ระวัง test ที่ mirror implementation: ถ้า implementation ผิดแต่ test ยังเขียว แปลว่า assertion อ่อนเกินไป

Dyad เป็นบทเรียนตรงจุด
test เดิมตรวจเพียงว่า promise resolve จึงผ่านแม้ระบบไม่รอ cleanup จริง การเพิ่ม test ที่ตรวจลำดับ side effect ทำให้ AC จับ defect ได้
Given: งานยังคลายตัว
When: consumer ขอปิด resource
Then: resource ยังเปิดจนถึง completion หรือ bound
แหล่งต้นทางหลัก

Dyad disposal regression commit

อ่านเพื่อดู: ดูการเปลี่ยน assertion จากแค่ resolve เป็นการตรวจลำดับพฤติกรรม

จำไว้

จำนวน test ที่เพิ่มไม่ใช่ acceptance criteria; ถ้าไม่บอก observable เราไม่รู้ว่าทดสอบอะไร

ลองตอบก่อนดูเฉลย

ส่วนใดทำให้ AC จับ implementation ที่ผิดแต่ยังดูเหมือนผ่านได้

เลือกคำตอบหนึ่งข้อ

ลงมือกับงานของคุณ

เขียน AC สองข้อให้ feature เดียว: หนึ่ง happy path และหนึ่ง failure/boundary case พร้อมระบุสิ่งที่ต้องสังเกต

เกณฑ์ตรวจตนเอง
  • มี Given, When และ Then ครบ
  • Then เป็น observable ที่วัด/สังเกตได้
  • มีกรณีที่อยู่นอก happy path
  • คนอื่นอ่านแล้วเลือกวิธีตรวจได้โดยไม่ต้องเดา

ถามครูได้เสมอ: ถ้าคำศัพท์หรือหลักฐานชิ้นไหนยังไม่ชัด ให้ถามต่อพร้อมคัดลอกประโยคหรือ link ที่ติดขัด ครูจะช่วยแยกข้อเท็จจริงจากข้อสังเคราะห์ให้
