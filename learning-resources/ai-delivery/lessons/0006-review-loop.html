ทักษะที่ใช้กับงานจริง

เปลี่ยน review comment ให้เป็นลูปแก้ที่ปิดได้

finding → ตรวจความจริง → decision → patch → ตรวจซ้ำ

ผลที่ฝึกได้ในบทนี้ คุณจะตอบ reviewer แต่ละ finding ด้วยสถานะและหลักฐาน ไม่ใช่แค่ ‘addressed’

เริ่มจาก finding ที่มี trigger → behavior ที่ผิด → ผลเสีย แล้วตัดสินว่า valid, invalid หรือ deferred ถ้า valid ให้ชี้ commit และการตรวจซ้ำ ถ้า invalid ให้แสดงหลักฐานหักล้าง ถ้า deferred ให้บอก follow-up กับเหตุผลที่งานปัจจุบันยังรับได้

ใน LiteLLM #40785 review ค้นพบว่า Responses input ไม่ถึง guardrail และ tool-call-only turn อาจ bypass policy แต่ละ finding กลายเป็น commit แยกที่มี test/behavior เพิ่ม ไม่ได้กลบด้วยคำอธิบายยาว ๆ

ตารางตัวอย่างที่สังเคราะห์เพื่อฝึก ไม่ใช่คำคัดลอกจาก thread:

FindingDecisionEvidence
R1: input ว่างvalidbridge commit + 400 assertion
R2: import ใน testinvalidpath และ sibling tests
R3: flag ยังไม่ใช้deferredcaveat + follow-up
แหล่งต้นทางหลัก

จำไว้

การตอบว่าปิดแล้วโดยไม่ผูกกับ final revision เปิดช่องให้ finding ยังอยู่ใน diff ใหม่

ลองตอบก่อนดูเฉลย

ลำดับใดทำให้ review เปลี่ยนเป็น feedback loop ที่ตรวจซ้ำได้

เลือกคำตอบหนึ่งข้อ

ลงมือกับงานของคุณ

เขียนคำตอบต่อ review finding สมมติหนึ่งข้อให้ครบ trigger, decision, code change, evidence และข้อจำกัด

เกณฑ์ตรวจตนเอง
  • finding มีอาการที่ reproduce หรือชี้ตำแหน่งได้
  • decision เป็น valid/invalid/deferred พร้อมเหตุผล
  • มี revision/commit ของการเปลี่ยน
  • บอกวิธีตรวจซ้ำและสิ่งที่ยังเหลือ

ถามครูได้เสมอ: ถ้าคำศัพท์หรือหลักฐานชิ้นไหนยังไม่ชัด ให้ถามต่อพร้อมคัดลอกประโยคหรือ link ที่ติดขัด ครูจะช่วยแยกข้อเท็จจริงจากข้อสังเคราะห์ให้
