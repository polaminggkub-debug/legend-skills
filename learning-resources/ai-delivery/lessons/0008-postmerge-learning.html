ทักษะที่ใช้กับงานจริง

เรียนจากสิ่งที่หลุดหลัง merge

artifact ที่ติดตั้งจริงต้องถูกตรวจด้วย consumer จริง

ผลที่ฝึกได้ในบทนี้ คุณจะออกแบบ post-merge verification ที่ไม่หยุดแค่ build หรือ manual workaround

หลัง merge ให้ถามว่า artifact ที่ผู้ใช้ได้รับเหมือนสิ่งที่เรา test ไหม ถ้างานคือ installer ให้รัน installer; ถ้างานคือ migration ให้เริ่มจาก state เก่า; ถ้างานคือ hardware fix ให้ consumer อย่าง libinput อ่านค่าที่ติดตั้งจริง

Omarchy #5435 ผ่านการทดสอบแบบ manual edit แต่หลัง merge packaged install path วางไฟล์ผิดที่ touchpad จึงยังไม่ทำงาน รอบแก้ #6388 จงใจวางไฟล์ .quirks ที่ผิดรูปแบบใน directory ที่ต้องการตรวจ แล้วเห็น parser ล้ม จึงยืนยันว่าระบบอ่านไฟล์นั้นจริง จากนั้นมีการตรวจบน hardware จริง โดย PR นี้ยังเปิดอยู่ ณ วันที่เก็บข้อมูล

รายงานอย่างซื่อสัตย์
แยก “path fix ได้รับการยืนยัน” ออกจาก “ทุกเครื่องมีสาเหตุเดียวกัน” และ “อาการดีขึ้นหลัง reboot” ออกจาก causality ที่พิสูจน์แล้ว
postmerge = packaged artifact
          + real consumer
          + stale state / non-target
          + observed limitation

ลงมือกับงานของคุณ

เลือกงานหนึ่งชิ้นที่คุณเคย merge แล้วออกแบบ post-merge probe: artifact, consumer, stale/non-target case และ limitation

เกณฑ์ตรวจตนเอง
  • ตรวจ artifact เดียวกับที่ผู้ใช้จะได้รับ
  • มี consumer หรือเส้นทางใช้งานจริง
  • มี stale state หรือ non-target case
  • แยกผลที่สังเกตได้ออกจาก causal claim

ถามครูได้เสมอ: ถ้าคำศัพท์หรือหลักฐานชิ้นไหนยังไม่ชัด ให้ถามต่อพร้อมคัดลอกประโยคหรือ link ที่ติดขัด ครูจะช่วยแยกข้อเท็จจริงจากข้อสังเคราะห์ให้
